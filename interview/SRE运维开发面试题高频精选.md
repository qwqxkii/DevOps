# SRE／运维开发面试题高频精选

> 适用方向：SRE、运维开发、DevOps、Kubernetes 平台、Linux 运维社招  
> 目标岗位：字节跳动、米哈游及同类互联网公司  
> 排序依据：真实面经重复度、岗位实际常见度、对生产实战的区分度。频率为经验分级，不是严格统计。  
> 推荐答法：**先说结论 → 解释原理 → 给出排查步骤或生产案例 → 补充预防措施**。

---

## 一、必问级：★★★★★

### 1. 请介绍你负责的业务和整体架构

不要只罗列 Nginx、Kubernetes、Redis。建议按下面顺序回答：

1. 业务是什么，用户量、QPS、数据量、集群规模是多少。
2. 流量入口：DNS/CDN/WAF/LB/Ingress。
3. 应用层：服务数量、调用关系、部署方式和发布方式。
4. 数据层：数据库、缓存、消息队列、存储。
5. 稳定性：监控、日志、链路追踪、限流、降级、容灾。
6. 自己负责什么，解决过什么核心问题，结果如何量化。

面试官真正想确认的是：你是否理解业务全链路，而不只是管理服务器。

### 2. 什么是 SRE？和传统运维、DevOps 有什么区别？

SRE 是用软件工程方法解决运维和可靠性问题，核心目标是在业务迭代速度与可靠性之间取得可度量的平衡。

- 传统运维更偏资源、部署、变更和故障处理。
- DevOps 是开发与运维协作的文化、流程和实践集合。
- SRE 是实现可靠性目标的一套工程方法，强调 SLI/SLO、错误预算、自动化、容量规划和事故复盘。

三者并不互斥。成熟团队通常同时使用 DevOps 协作方式、SRE 可靠性方法和平台工程能力。

### 3. SLI、SLO、SLA 和 Error Budget 分别是什么？

- **SLI**：服务水平指标，如成功率、P99 延迟、吞吐量、数据持久性。
- **SLO**：SLI 的目标，如“30 天内 99.9% 请求成功”。
- **SLA**：对客户的协议，未达到目标通常存在赔偿等后果。
- **错误预算**：允许失败的空间，通常为 `1 - SLO`。

例如 30 天、99.9% 可用性，允许不可用时间约为：

```text
30 × 24 × 60 × (1 - 0.999) = 43.2 分钟
```

错误预算充足时可以正常发布；消耗过快时应降低变更速度，优先修复可靠性问题。

### 4. 线上出现大量 5xx，你如何处理？

正确顺序是先止损，再定位：

1. 确认告警真实性、影响范围、起始时间和用户影响。
2. 检查是否与发布、配置、流量、依赖变更相关，暂停继续变更。
3. 必要时回滚、切流、扩容、限流或降级，先恢复核心业务。
4. 从入口到依赖逐层检查：LB/Nginx → 应用 → 缓存/MQ/数据库 → 外部依赖。
5. 对照 Metrics、Logs、Traces 和变更记录，形成假设并验证。
6. 恢复后验证核心接口和 SLI，保留现场，完成复盘和防复发措施。

不要一上来就“登录服务器看日志”，也不要在原因未明时反复重启。

### 5. 如何排查服务访问慢？

先区分是所有用户还是部分用户、所有接口还是单接口、持续还是偶发，然后分段测量：

- 客户端：DNS、TCP、TLS、首字节、下载时间。
- 接入层：CDN、LB、Nginx 排队和 upstream 时间。
- 应用层：线程池、连接池、GC、锁、CPU、下游 RPC。
- 数据层：慢 SQL、锁等待、缓存命中率、MQ 积压。
- 系统层：CPU、内存、I/O、网络丢包、重传、conntrack。

使用 P95/P99 分位数而不是只看平均值，通过 Trace 找到耗时最长的 Span，再结合日志和指标验证。

### 6. Linux load average 是什么？高负载怎么排查？

Linux load average 表示一段时间内处于可运行状态和不可中断睡眠状态的任务平均数量，不等于 CPU 使用率。

```bash
uptime
top
vmstat 1
pidstat -u -r -d -w 1
mpstat -P ALL 1
iostat -xz 1
```

- load 高、CPU 高：查热点进程、线程、系统态、上下文切换。
- load 高、CPU 不高：重点看 D 状态任务、磁盘/NFS I/O 和内核锁等待。
- 单核满而总 CPU 不高：检查单线程热点或中断集中。

### 7. CPU 使用率高如何定位？

先看是 user、system、iowait、steal 还是 softirq 高，再定位进程和线程：

```bash
top -H -p PID
pidstat -u -t -p PID 1
perf top
```

- user 高：业务计算、死循环、序列化、GC。
- system 高：系统调用、中断、网络包、锁竞争。
- iowait 高：任务等待块设备，但不能仅凭它断定磁盘故障。
- steal 高：虚拟机被宿主机抢占 CPU。

最后结合应用 profiling、火焰图和近期变更定位代码路径。

### 8. 内存持续升高或发生 OOM 怎么排查？

区分进程 RSS、Page Cache、共享内存、内核内存和容器 cgroup 使用量。查看 OOM 日志，确认是系统 OOM 还是 cgroup OOM：

```bash
free -h
cat /proc/meminfo
ps aux --sort=-rss | head
dmesg -T | grep -i -E 'oom|killed process'
cat /proc/PID/smaps_rollup
```

进程内存持续增长可能是泄漏、缓存无上限、连接未释放或流量增长。容器还要检查 requests/limits、QoS、工作集和节点内存压力。不要看到 `free` 小就直接认为内存不足，Linux 会利用空闲内存做缓存。

### 9. 磁盘满了，删除日志后空间为什么没有释放？

常见原因是文件已被删除，但仍被进程打开，空间要等文件描述符关闭后才释放：

```bash
lsof +L1
```

优先让程序重新打开日志或平滑重启，必要时再谨慎处理对应 fd。还要检查 inode、挂载点、保留块、容器层和快照：

```bash
df -h
df -i
du -xhd1 /path
```

### 10. TCP 为什么需要三次握手？为什么能可靠传输？

三次握手使双方确认彼此的发送和接收能力，并同步初始序列号；两次无法让服务端确认客户端已收到服务端的初始序列号，也更难避免历史报文造成错误连接。

TCP 依靠序列号、确认应答、校验和、超时重传、快速重传、滑动窗口、流量控制和拥塞控制实现可靠的有序字节流。可靠不代表永不失败，应用仍需设置合理的超时、重试和幂等。

### 11. TIME_WAIT 和 CLOSE_WAIT 过多分别说明什么？

- TIME_WAIT 出现在主动关闭方，用于处理迟到报文并保证最后 ACK 可重传。大量出现通常说明短连接多。
- CLOSE_WAIT 表示对端已关闭，而本地应用还没有关闭 socket；持续堆积通常是应用未正确释放连接。

```bash
ss -s
ss -ant state time-wait
ss -ant state close-wait
```

不能为了消除 TIME_WAIT 随意修改内核参数；应先检查连接复用、keepalive、连接池和应用关闭逻辑。

### 12. Nginx 出现 502、503、504 如何排查？

- **502 Bad Gateway**：无法建立 upstream 连接、连接被重置、响应格式异常等。
- **503 Service Unavailable**：无可用上游、主动限流或服务不可用。
- **504 Gateway Timeout**：已转发请求，但在超时时间内没有收到上游响应。

检查 access log 的 `$upstream_addr`、`$upstream_status`、`$request_time`、`$upstream_response_time`，再检查上游进程、端口、连接队列、超时、网络、DNS和依赖。状态码只能缩小范围，不能替代证据。

### 13. Nginx 常见负载均衡算法有哪些？如何让请求固定到一台机器？

- round robin：默认轮询。
- least_conn：优先连接数较少的实例。
- ip_hash：按客户端 IP 做粘性。
- hash key consistent：按 URI、Cookie 等键做一致性哈希。
- weight：结合权重分配流量。

固定到一台可用 `ip_hash`、对 Cookie/用户 ID 做 hash，或直接指定上游用于临时调试。生产中应尽量把会话放到共享存储，降低对粘性会话的依赖。

### 14. LVS 的 NAT、DR、TUN 模式有什么区别？

- NAT：请求和响应都经过 Director，需要改写地址，部署直观但 Director 更容易成为瓶颈。
- DR：Director 改写二层目的 MAC，请求经 Director，响应由 Real Server 直接返回；性能高，但通常要求同一二层网络并处理 ARP。
- TUN：通过 IP 隧道转发，可跨网段，Real Server 需支持隧道，响应通常直接返回。

面试中最好能画出请求和响应路径，并说明为何 DR 模式吞吐能力通常更强。

### 15. 监控系统应该监控什么？

按层次设计：

- 用户体验：可用性、错误率、P95/P99 延迟。
- 业务：订单成功率、登录成功率、核心流程转化。
- 服务：RED——Rate、Errors、Duration。
- 资源：USE——Utilization、Saturation、Errors。
- 依赖：数据库、缓存、MQ、第三方服务。
- 发布与容量：版本、实例数、资源水位、错误预算。

端口存活不等于服务可用，应使用健康接口、合成监控或真实业务探测。

## 二、高频级：★★★★☆

### 16. 怎样设计“有用”的告警，避免告警风暴？

告警应满足：用户或 SLO 受影响、需要人采取行动、包含上下文和 Runbook。优先基于症状告警，原因类指标用于诊断。

常用措施：持续时间窗口、分级、去重、分组、抑制、依赖收敛、维护窗口、动态阈值和多窗口错误预算燃烧率。每条 Pager 告警都应明确“现在必须做什么”，无行动价值的改成工单或日志。

### 17. Prometheus 的架构和数据采集过程是什么？

Prometheus Server 按配置主动拉取目标的 HTTP Metrics，写入本地 TSDB；Service Discovery 发现目标，PromQL 查询，Recording Rule 预计算，Alerting Rule 发送给 Alertmanager；Alertmanager 负责分组、抑制、静默和路由通知。

Pushgateway 主要适合短生命周期批处理任务，不应成为所有服务的默认推送入口。长期存储和全局查询通常结合 Thanos、Mimir、Cortex 等方案。

### 18. 为什么只看平均延迟不够？

平均值会掩盖长尾。例如 99% 请求为 20 ms，1% 请求为 5 s，平均数看起来可能仍可接受，但大量用户已经受影响。应同时看直方图和 P50/P95/P99，并关注分位数对应的流量、接口和地域。

Prometheus 中跨实例聚合延迟分位数通常应使用 Histogram 的 bucket 计算，而不是对各实例 Summary 的 quantile 直接求平均。

### 19. 一次完整的故障复盘应包含什么？

- 影响范围、用户影响、持续时间和 SLO 消耗。
- 精确时间线：发现、响应、止损、恢复。
- 根因、触发因素和放大因素。
- 哪些机制有效，哪些机制失效。
- 短期修复和长期 Action Items，明确负责人、截止时间和验收方式。

复盘应无责但不无行动。目标是改进系统和流程，而不是寻找背锅者。

### 20. 如何做容量规划？

从业务预测和 SLO 出发，确认单实例安全容量、峰值系数、增长率、冗余和故障场景。通过压测得到吞吐—延迟—错误率曲线，找到性能拐点，并为单机房/单节点故障预留容量。

持续监控 CPU、内存、I/O、连接数、队列和依赖容量，结合扩容耗时确定提前量。不能只按 CPU 平均值计算，也不能把自动扩缩容当成容量规划的替代品。

### 21. 发布导致故障，如何降低变更风险？

代码评审、自动测试、制品不可变、配置校验、小流量灰度、健康检查、核心指标对比、自动停止和一键回滚。数据库变更应尽量向前/向后兼容，采用 Expand-and-Contract，避免应用与 DDL 强绑定。

发布前明确负责人、观察窗口、回滚条件；发布后观察 SLI、错误率、延迟和资源，而不只是“Pod 都 Running”。

### 22. 限流、熔断、降级分别解决什么问题？

- 限流：限制进入系统的流量，保护容量。
- 熔断：下游持续失败时临时停止调用，避免资源被拖死。
- 降级：关闭非核心功能或返回兜底结果，保证核心链路。

三者常与超时、隔离、负载丢弃配合。重试必须有次数上限、退避和抖动，并考虑请求幂等，否则容易形成重试风暴。

### 23. RTO、RPO 是什么？如何设计容灾？

- RTO：故障后允许多长时间恢复服务。
- RPO：最多允许丢失多长时间的数据。

根据业务目标选择备份、主备、同城双活或异地多活。方案要覆盖 DNS/流量、应用、数据库、缓存、消息和配置，并定期做真实恢复演练。只有备份成功日志，没有恢复验证，不算可靠备份。

### 24. 进程、线程和协程有什么区别？

进程拥有独立虚拟地址空间和资源；同一进程内线程共享地址空间与大部分资源，但有各自栈和调度状态；协程通常由用户态运行时调度，切换成本更低，适合大量 I/O 并发。

线程共享资源带来锁、竞态和死锁问题。Python CPython 的 GIL 限制同一进程内多个线程同时执行 Python 字节码，但 I/O 密集任务仍可受益；CPU 密集任务可考虑多进程、原生扩展或其他语言。

### 25. 文件描述符耗尽有什么现象？怎么处理？

可能出现 `Too many open files`、新连接失败、无法打开日志等。检查系统级和进程级限制、当前 fd 数量及类型：

```bash
cat /proc/sys/fs/file-nr
cat /proc/PID/limits
ls /proc/PID/fd | wc -l
lsof -p PID
ss -s
```

根因常见于连接/文件泄漏或限制过低。不能只提高 `ulimit`，要验证应用是否正确关闭资源。

### 26. DNS 解析慢或偶发失败如何排查？

检查客户端配置、搜索域和 `ndots`，分别向各级 DNS 查询，比较 UDP/TCP、响应码和耗时：

```bash
dig example.com
dig +trace example.com
tcpdump -ni any port 53
```

关注缓存命中、上游超时、丢包、MTU、防火墙、conntrack、CoreDNS 资源和循环转发。在 Kubernetes 中还要检查 Pod 的 `/etc/resolv.conf`、CoreDNS 日志、Service/EndpointSlice 和 NodeLocal DNSCache。

### 27. HTTPS/TLS 握手大致过程是什么？

客户端发送支持的版本、密码套件和随机数；服务端返回选择结果、证书和密钥交换信息；客户端验证证书链、域名和有效期；双方通过密钥交换得到会话密钥，之后使用对称加密传输数据。

非对称密码主要用于身份认证和密钥协商，对称密码用于高效传输。TLS 1.3 减少了握手往返，并移除了多种旧算法。

### 28. Kubernetes 中 Pod 从提交到运行经历什么？

请求经认证、鉴权和准入后写入 etcd；Scheduler 为未调度 Pod 选择节点并绑定；目标节点 kubelet 观察到 Pod，通过 CRI 创建容器沙箱和容器，CNI 配置网络，CSI 挂载存储；kubelet 持续上报状态，控制器维护期望状态。

排障时按这个控制链逐层检查事件、调度条件、镜像、存储、网络、探针和应用进程。

### 29. readiness、liveness、startup probe 有什么区别？

- readiness 失败：从 Service 后端摘除，不重启容器。
- liveness 失败：kubelet 按重启策略重启容器。
- startup probe：保护慢启动应用；成功前不执行 liveness/readiness 的正常判断。

探针应反映对应语义。不要让 liveness 强依赖外部数据库，否则依赖故障可能触发大规模无效重启。

### 30. requests、limits、QoS 和 OOM 有什么关系？

requests 主要用于调度和资源保障；CPU limit 通常通过 CFS 配额节流，内存 limit 超过后可能触发 cgroup OOM。Pod 根据 requests/limits 组合被分为 Guaranteed、Burstable、BestEffort，节点资源紧张时会影响驱逐优先级。

排障要同时看容器限制、工作集、节点压力、OOM 事件和应用内存模型。盲目把 limit 设得很大可能降低节点稳定性。

### 31. Pod Pending、CrashLoopBackOff 怎么排查？

Pending：先看 Events，常见原因是资源不足、亲和/污点不匹配、PVC 未绑定、调度约束或镜像拉取前置问题。

CrashLoopBackOff：检查容器退出码、当前和上一次日志、Command/Args、配置、Secret、依赖、探针及 OOMKilled：

```bash
kubectl describe pod POD
kubectl logs POD -c CONTAINER --previous
kubectl get events --sort-by=.lastTimestamp
```

CrashLoopBackOff 是退避状态，不是根因。

### 32. CI/CD 与 GitOps 的典型流程是什么？

CI 完成代码检查、测试、构建、漏洞扫描并生成不可变制品；CD 将版本部署到环境。GitOps 以 Git 中的声明式配置作为期望状态，由 Argo CD/Flux 等控制器持续对账。

关键点包括：环境隔离、审批、Secret 管理、制品签名、灰度、指标门禁、审计和回滚。GitOps 不等于“自动同步一切”；生产环境仍要有清晰的变更控制策略。

### 33. Python 运维开发常考哪些基础？

重点准备：列表/集合/字典复杂度、生成器与迭代器、深浅拷贝、`is` 与 `==`、异常和上下文管理器、装饰器、线程/进程/协程、GIL、垃圾回收、HTTP/API、测试和日志。

不仅要背概念，还要能现场完成日志统计、并发探测、API 调用、数据去重和简单动态规划，并说明复杂度与异常处理。

## 三、场景进阶：★★★☆☆

### 34. 服务 A 调用 B 再调用 C，用户反馈慢，如何定位？

先用 Trace 确认耗时落在哪一跳；没有 Trace 时通过统一 request ID、各层访问日志和时间戳拼接链路。比较 A 自身处理、A→B 网络/B 排队、B→C 和 C 内部耗时，并检查超时、重试次数、连接池、线程池、DNS 和下游容量。

短期可扩容、降级、隔离或关闭重试止损；长期补齐链路追踪、依赖拓扑、超时预算和 SLO。

### 35. 如何安全迁移一个线上服务？

盘点依赖和数据 → 建立基线和验收指标 → 新环境部署与数据同步 → 小流量验证 → 分批切流 → 观察窗口 → 全量迁移 → 保留回退窗口 → 清理旧环境。

重点关注 DNS TTL、会话、消息重复、数据库双写一致性、配置/证书、容量、监控和回滚。迁移方案必须写清每一步的停止条件和回退动作。

### 36. 国内部署的动态业务要服务海外用户，如何优化？

静态内容使用海外 CDN；动态请求结合全球 DNS/Anycast、海外接入点、专线或云骨干优化。进一步可做海外多地域部署、数据就近读、异步写或多活，但需处理数据一致性、跨境网络波动、合规、成本和故障切换。

回答时不要只说“加 CDN”，因为 CDN 对动态请求和跨地域数据库访问的改善有限。

### 37. 如何排查网络丢包和重传？

先确定端到端哪一段异常，比较双向路径和不同时间段。检查接口丢包、错误、队列、系统软中断、TCP 重传、MTU、拥塞、ACL/NAT/conntrack：

```bash
ip -s link
ss -ti
sar -n DEV,TCP,ETCP 1
mtr -rwzc 100 HOST
tcpdump -ni any host HOST
```

抓包关注序列号、Duplicate ACK、Retransmission、窗口和 RTT。`mtr` 中间节点不回 ICMP 不一定代表真实业务丢包，应以终点和 TCP 证据为准。

### 38. etcd 故障为什么危险？如何保障？

etcd 保存 Kubernetes 集群期望状态和关键元数据。法定多数丢失会导致无法写入，磁盘延迟、空间告警、碎片和网络抖动也会影响 apiserver。

使用奇数成员、低延迟可靠磁盘、独立监控、定期快照和恢复演练；监控 leader 变化、提案延迟、fsync、DB 大小和剩余空间。恢复前要确认故障类型和集群身份，避免错误成员操作导致更大范围不可用。

### 39. 数据库连接数耗尽如何处理？

先确认活跃、空闲、长事务、锁等待和连接来源；保护管理连接，必要时限流、停止异常实例或终止明确的泄漏连接。检查应用连接池的最大值、超时、生命周期和实例数乘积。

长期方案是合理容量、连接池/PgBouncer、慢 SQL 和事务治理、连接水位告警。只提高数据库最大连接数可能把问题转化为内存和调度抖动。

### 40. 消息队列积压如何处理？

比较生产速率、消费速率和 Lag 趋势，确认是流量突增、消费者异常、下游变慢、分区不均还是毒消息。先恢复消费能力，可扩容消费者、隔离坏消息、降级下游或限流生产者。

扩容前确认分区数、顺序性和幂等；清理积压要评估过期数据、重复消费和对下游的二次冲击。事后补齐端到端延迟 SLO 和容量预案。

### 41. 如何设计自动化运维工具？

先明确输入、权限边界、幂等性和失败模型，再设计 dry-run、审批、分批执行、超时、重试、熔断、回滚、审计和指标。高风险操作要限制目标范围并保留人工中止能力。

面试项目可讲 K8s 巡检、批量变更、Prometheus Exporter、容量分析或故障自愈，但必须说明解决了什么痛点、规模多大、失败时怎样保证安全、最终节省了多少时间或降低了多少故障。

### 42. 你处理过最严重的一次事故是什么？

使用 STAR 加事故时间线回答：

- 背景和影响：业务、用户、持续时间、损失或 SLO。
- 你的职责：你在响应中负责什么。
- 行动：如何发现、止损、定位、协调和恢复。
- 根因：技术根因、触发因素、为何防线未拦住。
- 结果：恢复耗时、改进措施和量化效果。

不要虚构“大事故”。小故障只要分析完整、改进有效，同样能体现能力。

## 四、行为与项目题：必须准备

### 43. 为什么选择 SRE／运维开发？

结合自己的经历回答：喜欢从系统全局解决稳定性问题，愿意通过代码减少重复劳动，并能在故障压力下基于证据推进恢复。避免只回答“喜欢 Linux”或“开发太卷”。

### 44. 你的优势和不足是什么？

优势要有证据，例如“Linux/网络排障强”后面接真实案例。不足应真实但可改善，并说明行动和进展，例如正在用 Go 补齐平台开发能力；不要把岗位核心能力说成完全不会。

### 45. 你开发过什么工具或平台？

按“痛点—设计—难点—安全性—结果”介绍。面试官常继续追问数据模型、并发、权限、异常、测试、部署、监控和高可用，因此只使用脚手架拼页面而不了解后端实现很难过关。

## 五、低收益题目：建议降级准备

以下内容并非没用，但对当前 SRE/运维开发社招的投入产出较低，除非 JD 或项目明确涉及：

- Open-Falcon、Puppet、SaltStack 的内部架构细节。
- Vue 生命周期、CSS 盒模型等前端细节。
- 背诵 TCP/IP 每个首部字段的位数。
- 冷门 Python 魔法方法和解释器内部优化细节。
- 单纯背所有 HTTP 状态码。
- 不结合生产场景的工具优劣对比。

旧面经中的 Open-Falcon、Puppet 等问题可转化为现代能力：Prometheus/可观测性、声明式配置、GitOps 和平台工程。

## 六、面试前速记清单

面试前确保可以脱稿回答：

- 画出自己负责业务的完整架构和调用链。
- 讲清 SLI、SLO、SLA、错误预算及一个计算示例。
- 讲清一次 5xx 或延迟故障的止损和定位过程。
- Linux CPU、load、内存、磁盘、fd 的排障路径。
- TCP 握手、重传、TIME_WAIT/CLOSE_WAIT、TLS。
- Nginx 502/503/504、负载均衡；LVS NAT/DR。
- Prometheus 架构、RED/USE、P99、告警降噪。
- Kubernetes Pod 创建、探针、资源、Pending/CrashLoop 排障。
- 发布、回滚、容量、容灾、复盘。
- Python/Go 完成一段日志或 API 类编码题。
- 准备 2 个项目和 2 个故障案例，全部包含量化结果。
